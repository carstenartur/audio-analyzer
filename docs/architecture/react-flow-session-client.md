# React Flow collaboration-session client

Status: Implemented by issues #270 and #272  
Depends on: session lifecycle #241, ordered SSE #242, production frontend #269, durable history #284

## Purpose

This document records the production browser boundary for collaboration sessions. React Flow remains a rendering/input adapter over server-owned workflow projections; it does not become a second workflow engine, presence authority, semantic undo stack or persistence layer.

## Startup and restore modes

The workbench starts with the deterministic seed projection from the legacy single-workflow endpoint. That graph is useful for orientation, documentation screenshots and catalog discovery, but semantic controls are read-only.

Editing is enabled only after all of the following are true:

1. a stable actor identity exists;
2. the browser has created or joined a server session;
3. the canonical session projection has loaded;
4. the ordered SSE connection reports `live`;
5. no ordinary semantic command is currently pending.

The active session id is retained per browser tab in session storage when available. A full page reload attempts to rejoin that session using the same actor identity. Failure clears the remembered session rather than constructing browser-local workflow or history state.

## Actor and session lifecycle

The browser stores `actorId`, `userId` and `displayName` per browser tab in session storage when available. Identity cannot change while a session is active because server membership, history capability selection and operation authorship use the actor id as a stable key.

The collaboration panel maps directly to the lifecycle API:

```text
create  -> POST   /workflow/sessions
join    -> POST   /workflow/sessions/{id}/join
leave   -> POST   /workflow/sessions/{id}/leave
close   -> DELETE /workflow/sessions/{id}
inspect -> GET    /workflow/sessions/{id}
project -> GET    /workflow/sessions/{id}/projection
```

The UI never infers ownership or mode transitions. It displays the immutable mode returned by the server and enables close only for the reported owner; the server remains the final authorization boundary.

## Ordinary semantic command flow

Each React Flow gesture is converted into one existing semantic operation payload:

```text
CreateNode
ConnectPorts
DisconnectPorts
UpdateProperty
```

The request contains:

- a collision-resistant operation id generated once for the gesture;
- the joined actor metadata;
- the immutable session mode;
- the last accepted semantic revision;
- no layout, cursor or persistence implementation data.

The browser shows `pending` until the command response arrives. Rejected responses never mutate React Flow state. Accepted responses may update the projection immediately, while the matching SSE event remains responsible for ordered sequence advancement and remote convergence.

A follow-up metadata read supplies the actual accepted revision. This matters for idempotent retries: replaying an already accepted operation id must not invent another local revision.

## Durable undo and redo discovery

The browser does not derive semantic undo or redo from React component state, received SSE events or a Yjs undo manager. On join, full reload, reconnect, semantic revision change and accepted history command it queries:

```text
POST /workflow/sessions/{id}/history/capabilities
POST /workflow/sessions/{id}/history/query
```

Capabilities report the actor's current personal undo and redo targets, their availability, blockers, reconstructibility and the revision at which those facts were computed. Shared-undo mode additionally exposes a paginated newest-first target browser. The browser displays legacy body-less operations but never treats them as executable.

The immutable mode determines the visible controls:

- `PRIVATE_WORKSPACE`: personal undo and redo from the owner's durable history;
- `SHARED_SESSION_PERSONAL_UNDO`: personal undo and redo while all accepted changes remain visible;
- `SHARED_SESSION_SHARED_UNDO`: explicit target selection from durable shared history.

No browser-side fallback skips a blocked or non-reconstructible target.

## Preview and confirmation

Every visible button and keyboard shortcut enters the same preview path:

```text
POST /workflow/sessions/{id}/undo/preview
POST /workflow/sessions/{id}/redo/preview
```

The accessible confirmation dialog shows operation type, actor, timestamp, affected semantic objects, preview revision and every later blocking operation. Unsafe previews cannot be confirmed.

Shared undo requires all of the following:

1. the user explicitly selects one active durable history row;
2. the server returns a fresh preview for that exact target;
3. the user acknowledges that the shared canonical workflow changes for all participants;
4. the command submits the preview identity and expected revision.

Ctrl/Cmd+Z and Ctrl/Cmd+Shift+Z or Ctrl/Cmd+Y only open these same preview and confirmation paths. In shared mode, a shortcut without an explicitly selected target shows an instruction instead of choosing one automatically.

## Stable command identity and uncertain transport

A history command envelope is generated once and contains:

- `UNDO` or `REDO`;
- a stable `commandId`;
- expected revision;
- exact target operation;
- shared undo preview id where required.

A structured HTTP error is a definitive rejection and clears the pending envelope. A network failure before a response is ambiguous: the envelope remains visible with its exact command id. The browser reconciles the canonical session and reloads durable history. If that history contains the command id, acceptance is proven and the pending state clears. Otherwise the UI offers retry of the exact same envelope; it never generates a replacement id.

Accepted command responses do not make the browser authoritative. The collaboration controller reconciles session metadata and canonical projection, then reloads history capabilities. A failure in that follow-up reload is reported as a synchronization problem, not as retroactive command rejection.

## Ordered SSE and reconciliation

The client subscribes to:

```text
GET /workflow/sessions/{id}/events?afterSequence={lastAcceptedSequence}
```

Named events are reduced by a framework-independent state function covered by Node-native tests.

Rules:

- an event with an already accepted sequence is ignored as a duplicate;
- the next contiguous event is applied;
- a non-snapshot sequence gap triggers metadata plus projection reconciliation;
- `SNAPSHOT` always replaces the local sequence, revision and projection;
- a snapshot may legitimately move sequence backwards when a restarted server receives a cursor ahead of its current event window;
- revision/sequence conflicts returned by REST also trigger canonical reconciliation;
- reconnect uses bounded exponential delay and resumes from the latest accepted sequence.

The browser never fills a missing event by replaying local gestures or merging graph objects heuristically.

## Presence boundary

Cursor, selection and viewport hints are merged and throttled before being sent to:

```text
PUT /workflow/sessions/{id}/presence
```

Presence events update an actor-scoped view separate from the workflow projection. Remote samples expire locally after a short TTL. Expiration removes only the visual sample, not participant membership, semantic revision, event history, workflow DSL or Git state.

Leaving, closing or receiving `SESSION_CLOSED` clears pending presence buffers and closes the event transport.

## Browser diagnostics and test hooks

The maintained UI exposes stable hooks for:

- create, restore, join, leave and close actions;
- active session id and immutable mode;
- connection and reconnect state;
- semantic revision and event sequence;
- ordinary pending/accepted/rejected command state;
- durable capability revision and history controller state;
- personal undo, redo and shared target selection;
- confirmation, blockers, stale or non-reconstructible targets;
- uncertain command id and exact retry;
- participant list and remote presence samples.

Framework-independent Node tests cover history state reduction, capability-derived control policy, uncertain command resolution, exact request envelopes and keyboard route selection. TypeScript, architecture-boundary lint and the production Vite build validate the React adapter. Process-level two-browser coverage remains owned by #249.

## Explicit exclusions

This client does not implement:

- semantic undo/redo domain policy or durable append behavior;
- a browser-local or Yjs semantic undo manager;
- live-session checkpoint semantics;
- browser-side DSL parsing;
- JGit, Hibernate or database access;
- cross-process test orchestration duplicated from #249.
