# Workbench screenshot documentation pipeline

Web-workbench screenshots in public documentation are generated by executable integration scenarios. They are not manually captured mock-ups.

## Architecture

```text
Maven (-Pscreenshot-tests)
  -> builds audio-app and verified audio-web-editor assets
  -> Testcontainers starts the packaged Spring Boot workbench
  -> Java Playwright launches headless Chromium
  -> scenario creates and asserts the documented state
  -> screenshot is captured only after those assertions pass
  -> ScreenshotPipeline compares or updates the PNG baseline
  -> documentation embeds the committed image
```

The browser tests reuse the same packaged application, HTTP/SSE adapters and production web assets as the collaboration E2E suite.

## Operating modes

### Verify mode

```bash
./mvnw -Pscreenshot-tests verify
```

Verify mode:

- starts the packaged workbench through Testcontainers;
- captures generated images into a temporary directory;
- compares them with `docs/assets/screenshots/workbench/`;
- fails on a missing baseline, dimension mismatch or excessive pixel difference;
- writes generated failure images under `workbench-screenshot-tests/target/screenshot-failures/`.

### Update mode

```bash
./mvnw -Pscreenshot-tests verify -DupdateScreenshots=true
```

Update mode runs the same assertions but writes the resulting images to the committed baseline directory. It must be invoked intentionally and reviewed like source code.

A user-visible change should update together:

1. production UI;
2. integration scenario;
3. committed PNG baseline;
4. user documentation;
5. architecture documentation when the behavior boundary changed.

Hand-edited screenshots are not equivalent evidence.

## Synchronization discipline

Screenshot scenarios contain no fixed-delay `sleep`, `Thread.sleep` or `waitForTimeout` calls.

A scenario advances only when an observable contract is true, for example:

- session identity is visible;
- ordered SSE reports `live`;
- semantic revision reaches the expected value;
- a canonical node appears;
- durable capability revision is current;
- a preview or confirmation dialog is visible;
- a button has the expected enabled state.

Playwright timeouts are upper failure bounds. They do not determine when capture occurs.

## Volatile UI content

Scenarios use deterministic workflow/session names and actor identities. Animations and blinking carets are disabled before capture.

Where production UI must display volatile information, use the narrowest truthful mechanism:

1. deterministic test data when the value belongs to the scenario;
2. semantic markup plus test-only normalization for presentation-only timestamps;
3. a masked region when the content is irrelevant to the documented feature;
4. a scoped component screenshot when surrounding state adds no value.

Durable-history timestamps use `<time class="history-timestamp" dateTime="…">` in production markup. `WorkbenchHistoryScreenshotIT` replaces only their displayed text with a fixed documented instant after asserting the real preview state. The production value and command semantics are not mocked.

## Comparison strategy

- Default tolerance: 2% of total pixels, configurable through `-Dscreenshot.tolerance.pct=N`.
- Per-channel differences up to 8 tolerate minor anti-aliasing changes.
- A dimension mismatch is a complete mismatch.
- Full-viewport images are used when the surrounding application context matters.
- Scoped locator images are preferred when they improve readability without hiding required context.

## Configuration

|      System property       |                 Default                 |                      Purpose                       |
|----------------------------|-----------------------------------------|----------------------------------------------------|
| `updateScreenshots`        | `false`                                 | Write new committed baselines instead of comparing |
| `screenshot.tolerance.pct` | `2`                                     | Allowed pixel-difference percentage                |
| `docs.screenshots.dir`     | `docs/assets/screenshots/workbench`     | Baseline directory                                 |
| `workbench.jar.path`       | packaged `audio-app` JAR                | Application under test                             |
| `workbench.lib.dir`        | `audio-app/target/lib`                  | Runtime dependency directory                       |
| `workbench.static.dir`     | `audio-web-editor/target/frontend-dist` | Verified production assets                         |

## Documented scenarios

### Initial workbench load

`WorkbenchInitialLoadIT` opens the deterministic orientation graph:

```text
Synthetic Signal Generator -> Gain -> Localization
```

It verifies the palette, rendered nodes, typed ports and successful load status.

Generated images:

- `initial-load.png`
- `node-palette.png`

### Live collaboration session

`WorkbenchCollaborationScreenshotIT`:

1. injects a stable actor identity;
2. creates a personal-undo shared session;
3. waits for ordered SSE;
4. submits generator and gain operations;
5. verifies canonical projection, revision and participant state;
6. captures `collaboration-session.png`.

### Personal semantic undo preview

`WorkbenchHistoryScreenshotIT.personalUndoPreviewShowsServerOwnedImpactBeforeConfirmation`:

1. creates a personal-undo session;
2. appends a generator and gain node;
3. waits for revision and durable capability revision 2;
4. opens the authoritative undo preview;
5. verifies actor, operation and enabled confirmation;
6. normalizes presentation-only timestamp text;
7. captures `collaboration-personal-undo-preview.png`.

### Shared semantic undo preview

`WorkbenchHistoryScreenshotIT.sharedUndoPreviewShowsExplicitTargetAndAcknowledgement`:

1. creates two isolated browser actors;
2. creates and joins a shared-undo session;
3. appends one canonical operation;
4. proves no target is selected automatically;
5. selects the operation and requests a fresh preview;
6. proves confirmation remains disabled without acknowledgement;
7. captures `collaboration-shared-undo-preview.png`.

These two images are embedded in the README and [Collaborative workflow design](features/collaborative-workflows.md).

## Adding a scenario

1. Add or extend a `*IT.java` test annotated with `@Tag("screenshot")`.
2. Drive the packaged application to a deterministic user-visible state.
3. Assert the semantic state, not merely that a component exists.
4. Normalize only explicitly identified presentation volatility.
5. Call `ScreenshotPipeline.processScreenshot(...)`.
6. Run update mode and inspect the PNG visually.
7. Commit test, baseline and documentation together.
8. Run verify mode from a clean checkout.

## Visual acceptance

Reject a screenshot when:

- labels, object ids or controls are clipped;
- text contrast is insufficient;
- the important graph or dialog is obscured;
- a surrounding empty state contradicts the documentation;
- generated timestamps or identifiers make the image irreproducible;
- the scenario did not assert the state described by the text;
- the viewport hides required confirmation or conflict information.

Follow the [screenshot QA checklist](qa/screenshot-qa-checklist.md).

## CI integration

The normal Maven workflow remains Docker-free. Screenshot verification is opt-in because it installs Chromium and starts a containerized packaged application.

A dedicated workflow should:

- build the packaged application and optional browser-test reactor;
- install the pinned Playwright Chromium runtime;
- run screenshot tests in verify mode;
- upload Failsafe reports and generated failure images;
- never rewrite baselines silently.

An update workflow may commit generated PNGs only when intentionally invoked for one reviewed change. Temporary update workflows must remove themselves.

## Layer boundaries

|                           Allowed                            |                       Forbidden                        |
|--------------------------------------------------------------|--------------------------------------------------------|
| Testcontainers and Playwright in the test module             | Playwright types in audio/workflow domain modules      |
| Stable production selectors                                  | Test-only semantic endpoints                           |
| Test-only deterministic identities and display normalization | Replacing canonical server state with browser fixtures |
| Committed generated PNGs                                     | Hand-edited or unreproducible screenshots              |
| UI and semantic assertions before capture                    | Sleep-driven screenshots                               |
| Visual review plus pixel comparison                          | Treating pixel comparison alone as product correctness |
