# QA findings and remaining technical debt

This document records the current product-hardening state. It is not a claim that every interactive path, hardware combination or static-analysis finding has been eliminated.

## Current QA position

The repository now has two distinct user-facing surfaces:

- a Swing audio signal workbench;
- a packaged React Flow workflow workbench.

The public documentation has been reorganized around audio-processing tasks. Detailed implementation and plugin material is linked from dedicated pages instead of dominating the README.

## Confirmed documentation and code alignment

- The default reactor includes `audio-core`, `audio-geometry`, `audio-acquisition`, `audio-dsp`, `audio-plugin-api`, `audio-experimental-acoustic`, `audio-web-editor` and `audio-app`.
- `audio-plugin-api` remains isolated from concrete host and audio modules; the host discovers providers through `ServiceLoader`.
- `audio-experimental-acoustic` remains optional research code.
- The React Flow client is an adapter over server-owned canonical workflow state.
- Session restore, SSE catch-up and personal/shared semantic undo/redo are exercised with two isolated Chromium contexts.
- Durable history screenshots are generated by packaged-application integration scenarios after semantic state assertions.
- Collaboration-history timestamps use semantic `<time>` markup and are normalized only in screenshot tests.
- Codecov upload remains informative rather than a hard artifact gate.

## Evidence added for collaboration

The collaboration E2E suite proves:

- cross-browser canonical projection convergence;
- remote presence outside workflow state;
- stale expected-revision rejection;
- controlled SSE interruption and replay/catch-up;
- full reload and active-session restoration;
- personal undo and redo;
- explicit shared target selection, acknowledgement, undo and redo.

The suite uses no fixed-delay sleeps. Failures publish browser screenshots, HTML, console/network logs, Playwright traces and server logs.

Generated and visually reviewed documentation states now include:

- live collaboration session;
- personal semantic undo preview;
- shared semantic undo preview with disabled confirmation before acknowledgement.

## Remaining technical debt

### Durable cross-process restart

Issue #249 remains open for the full process-restart stage. Browser tests still need to prove durable Hibernate/JGit recovery across application shutdown and restart, including pending outbox dispatch and checkpoint/history behavior where applicable.

### Manual application QA

A human tester still needs to run a packaged release candidate and record a dated QA matrix for:

- desktop startup and deterministic demo input;
- real input device selection and error handling;
- recording, replay and evidence export;
- plugin discovery and contributed views;
- web workbench usability at common viewport sizes;
- HiDPI and desktop resizing;
- acoustic simulation and imported-recording workbenches.

### Screenshot review

Automated comparison cannot prove semantic readability. Every changed baseline still requires visual review for:

- clipped labels or controls;
- low contrast;
- misleading empty states;
- hidden confirmation/conflict details;
- inconsistent surrounding documentation.

An offline documentation link checker is still desirable.

### Static analysis and coverage

- Existing Checkstyle, PMD and SpotBugs debt remains baseline-managed.
- The JaCoCo floor is intentionally conservative and should rise only with behavior-focused tests.
- Broad exclusions must not replace local fixes or narrow documented rationale.

### Architecture

- `org.hammer.audio` remains split across application and DSP code and should be resolved before JPMS modularization.
- Legacy compatibility models remain in selected desktop paths.
- Search, semantic merge and actual immutable workflow execution remain open roadmap slices.

### Timing and localization

- `SampleClock` still represents nominal timing rather than a complete drift/jitter correction framework.
- Acoustic localization is validated mainly with deterministic simulations and selected recordings.
- Real microphone-array or species claims require synchronized hardware, calibrated geometry and repeatable benchmark evidence.

## Required release checks

Before public release messaging:

1. run `./mvnw clean verify` and CodeQL;
2. run relevant collaboration and screenshot workflows;
3. verify persistent migrations/recovery when durable mode is included;
4. visually review generated images;
5. complete a dated manual application QA record;
6. verify README commands from a clean checkout;
7. document remaining limitations rather than hiding them.
